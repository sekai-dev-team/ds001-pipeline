# DS-001 v0.4.3: Per-Article LLM Filter (Break Batch)

## Problem

v0.4.2 batch design sends 50 articles per API call → JSON parsing fails for entire batch if one result is malformed. Structured summaries need more output tokens, making batching worse.

## Design: Per-Article API Calls

Each article gets its own LLM call. One call = one JSON object (not array). No cascading failures.

## Requirements

### 1. Single-article prompt
- Rewrite `_call_deepseek()` to take ONE article → return ONE result dict
- System prompt stays same, but output is `{relevant, ai_summary, content_type}` (object, not array)
- `max_tokens`: 1024 per call (one article's summary is ≤400 chars)

### 2. Concurrency model
- Use `concurrent.futures.ThreadPoolExecutor` with `max_workers=5`
- 5 parallel calls max — won't overload DeepSeek API or k-mcp
- Each call has `timeout=60` (single article should be fast)

### 3. Error isolation
- If one article's call fails (timeout, JSON parse error), log warning and mark `relevant=False`
- Other articles continue unaffected
- Track `success_count` and `error_count` in logs

### 4. k-mcp write rate limiting
- After LLM filter, batch writes to k-mcp in groups of 10
- 500ms delay between k-mcp write batches (prevents OOM from bulk reindex)
- (This may already be handled in knowledge_mcp.py — verify)

### 5. Clean up
- Remove `MAX_ARTICLES_PER_BATCH` constant (no longer needed)
- Remove batch-sorting logic in `filter_articles()`
- Simplify `filter_articles()` to iterate articles with ThreadPoolExecutor

## Files

| `pipeline/llm_filter.py` | Per-article design, ThreadPoolExecutor, single-object JSON output |

## Acceptance

- 100 articles processed in ~20 API calls parallel (5 workers)
- No batch-level failures — individual article failures don't affect others
- k-mcp not OOM during write phase
